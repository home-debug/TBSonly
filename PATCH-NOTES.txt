Performance audit v1 - si2183.c (2026-09-20, ~00:20):
  Static audit of si2183.c from latest found:
  1) si2183_get_tune_settings: min_delay_ms = 900 -> BLIND wait after every
     zap. Si2183 firmware reports lock quickly -> 900ms is pure latency.
     Patch: 300ms. BIGGEST gain (up to ~0.6s per zap).
  2) si2183_tune: *delay = HZ/5 (200ms) -> HZ/10 (100ms) - more frequent
     status reads while searching (~100ms faster detection on average).
  3) [unchanged] cmd_execute busy-polls I2C without sleeping - kept,
     adding usleep would add latency to every command.
  4) [unchanged] firmware download on first attach - hardware protocol.
  Both patches in kernel-patches.sh (idempotent, unique markers).
  NOTE: user's cards do NOT use si2183 - v1 kept for other cards only.

Performance audit v2 - gx1133.c + cx24117.c (2026-09-20, ~00:30):
  (both cards verified via user's lsmod: gx1133=TBS6902,
   cx24117=TT S2-4100/TBS6922, both with av201x tuner, tas2101 LNB)
  gx1133.c (TBS6902):
   - initfe: 4x reset msleep(10) -> msleep(3)      [once per adapter open]
   - set_frontend: tuner PLL settle msleep(50) -> 10 (AV201x locks in ~1-2ms)
   - lock poll: 20ms x 15 -> 10ms x 30 (same 300ms worst case)
   - tune poll *delay HZ/5 -> HZ/10
  cx24117.c (TBS6922):
   - cmd_execute_nolock: EXECUTE busy-wait msleep(20) -> usleep_range(900,1100)
     EVERY FW command paid ~10-19ms dead tick; a zap issues 4-6 commands
   - set_frontend lock wait: 20ms x 50 -> 10ms x 100 (same 1s bound,
     matters for DVB-S2 ROLLOFF_AUTO = up to 3 attempts, worst case was 3x1s)
   - tune poll *delay HZ/5 -> HZ/10
  NOT touched (spec/risk): msleep(100) in set_voltage (DiSEqC spec),
  diseqc send/burst timings, root_2_gold (rarely called), fw download.
  Expected real gain: ~150-350ms per zap (path dependent),
  mostly from cx24117 EXECUTE poll + gx1133 PLL settle + poll granularity.
  All A/B testable; revert = removing the block from kernel-patches.sh.

Safety - TBS_PERF=1 gate (2026-09-20, ~00:35):
  - User asked "are you sure this will not cause harm" - the honest answer:
    not 100%; highest risk = gx1133 tuner settle 50->10ms (PLL physics on
    weak transponders), the rest low/very low.
  - NO patch touches the data path or registers - only timing.
  - DECISION: all performance patches (v1 si2183 + v2 gx1133/cx24117)
    moved behind a gate:  TBS_PERF=1 sudo bash install_tbsdtv-smart.sh
    Default OFF -> a plain build uses vanilla TBS sources.
  - TECHNICAL NOTE: revert requires the flag OFF + rm -rf /usr/src/tbs-drivers
    (patches modify the sources on disk, a rebuild alone does not restore
    the originals).
  - A/B plan: build 1 without TBS_PERF (baseline sanity), build 2 with
    TBS_PERF=1, zap-time measurement before/after, decide whether it stays.
