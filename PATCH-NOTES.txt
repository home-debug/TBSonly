Performance audit v1 - si2183.c (2026-09-20, ~00:20):
  Static audit of si2183.c from latest found:
  1) si2183_get_tune_settings: min_delay_ms = 900 -> BLIND wait after every
     zap. Si2183 firmware reports lock quickly -> 900ms is pure latency.
     Patch: 300ms. BIGGEST gain (up to ~0.6s per zap).
  2) si2183_tune: *delay = HZ/5 (200ms) -> HZ/10 (100ms) - more frequent
     status reads while searching (~100ms faster detection on average).
  3) [unchanged] cmd_execute busy-polls I2C without sleeping - kept,
     adding usleep would add latency to every command.
  4) [unchanged] firmware download on first attach - hardware protocol.
  Both patches in kernel-patches.sh (idempotent, unique markers).
  NOTE: user's cards do NOT use si2183 - v1 kept for other cards only.

Performance audit v2 - gx1133.c + cx24117.c (2026-09-20, ~00:30):
  (both cards verified via user's lsmod: gx1133=TBS6902,
   cx24117=TT S2-4100/TBS6922, both with av201x tuner, tas2101 LNB)
  gx1133.c (TBS6902):
   - initfe: 4x reset msleep(10) -> msleep(3)      [once per adapter open]
   - set_frontend: tuner PLL settle msleep(50) -> 10 (AV201x locks in ~1-2ms)
   - lock poll: 20ms x 15 -> 10ms x 30 (same 300ms worst case)
   - tune poll *delay HZ/5 -> HZ/10
  cx24117.c (TBS6922):
   - cmd_execute_nolock: EXECUTE busy-wait msleep(20) -> usleep_range(900,1100)
     EVERY FW command paid ~10-19ms dead tick; a zap issues 4-6 commands
   - set_frontend lock wait: 20ms x 50 -> 10ms x 100 (same 1s bound,
     matters for DVB-S2 ROLLOFF_AUTO = up to 3 attempts, worst case was 3x1s)
   - tune poll *delay HZ/5 -> HZ/10
  NOT touched (spec/risk): msleep(100) in set_voltage (DiSEqC spec),
  diseqc send/burst timings, root_2_gold (rarely called), fw download.
  Expected real gain: ~150-350ms per zap (path dependent),
  mostly from cx24117 EXECUTE poll + gx1133 PLL settle + poll granularity.
  All A/B testable; revert = removing the block from kernel-patches.sh.

ROOT CAUSE #2 - header source mismatch (2026-09-20, clean build):
  - Symptom: dvb_frontend.c failed with "no member named modcode",
    "MODCODE_ALL undeclared", "FE_READ_TEMP undeclared", "no member named
    set_property" etc.
  - Fetched the REAL frontend.h from TBS latest - it DOES contain all these
    extensions (DTV_MODCODE, MODCODE_ALL, FE_READ_TEMP, FE_ECP3FW_READ,
    FE_24CXX_READ, struct dvb_frontend_ops with read_temp/spi_read/spi_write/
    mcu_read/set_property).
  - But H1/H2 pointed to $KHEADERS_COMMON (distro), which on Debian is the
    arch-specific headers package that lacks include/media/dvb_frontend.h
    entirely (cp: cannot stat), and even -common has only the vanilla kernel
    frontend.h without TBS extensions.
  - So the compiler fell back to the system /usr/include/linux/dvb/frontend.h
    (vanilla), causing all the missing-member errors on a from-scratch build.
  - Why it "worked" before: previous builds reused stale .o files from an
    earlier build (dirty tree), so the compile never re-ran from zero.
  - FIX: H1/H2 -> $SRC/include/media/dvb_frontend.h and
    $SRC/include/uapi/linux/dvb/frontend.h (TBS tree). $SRC is guaranteed to
    exist at that point (fetch precedes patches).

Include path fix for clean builds (2026-09-20):
  - dvb_frontend.c and several frontends still failed with missing TBS
    extensions even after H1/H2 pointed at the TBS tree, because the
    compiler never saw ${SRC}/include in its search path.
  - KCFLAGS alone is not reliable for -I injection in kbuild external-module
    builds; KBUILD_CPPFLAGS is honored. Also the isolated BUILD_DIR was
    seeded from KHEADERS_COMMON first, which can shadow the TBS uapi copy.
  - FIX: (1) add -I${SRC}/include -I${SRC}/include/uapi to EXTRA_CFLAGS;
    (2) pass KBUILD_CPPFLAGS="-I${SRC}/include -I${SRC}/include/uapi" to
    every per-target make invocation.
  - This is what allowed from-scratch builds to finally resolve the TBS
    frontend.h extensions (modcode, set_property, read_temp, ecp3/eeprom
    ioctls) without relying on stale objects.
